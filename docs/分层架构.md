# 分层架构

RKFlash 有三个平台版本。Linux 与 Windows 共用一套 Rust 代码，macOS 是 SwiftUI 原生版。
仓库按两条原则组织：

1. **平台差异单独成包**：三个系统各自的代码、界面配置和打包脚本全部放在 `platforms/<系统>/`，
   通用代码（`crates/`）不含任何平台条件编译。
2. **通用部分分层解耦**：前端、契约、应用、运行时、领域逐层依赖；前端与后端只通过 `api` 交互，
   且 api 的每个模块与前端的一个功能区一一对应。

## 目录

```text
crates/                    通用代码（与平台无关）
  core/                    领域：固件解析、分区表、芯片识别、rkdeveloptool 协议、烧录工作流
  api/                     契约：前后端唯一接口，按功能区分模块
  config/                  契约：工作区配置模型与 JSON
  application/             应用：用例实现（service/）、校验、执行计划、端口
  runtime/                 通用基础设施：进程执行、设备轮询、日志、持久化、装配
  frontend/                界面：egui 视图、动作层（actions/）、组件、主题
  launcher/                启动：按目标系统选择一个平台包
platforms/                 三个系统的全部差异，每个系统一个目录，互不依赖
  linux/                   upgrade_tool 适配器、Unix 宿主、桌面配置；packaging/ → .deb
  windows/                 rkdeveloptool 适配器、Win32 宿主、桌面配置；packaging/ → 安装程序与 zip
  macos/                   SwiftUI 原生应用、Xcode 工程与 Makefile → .dmg
third_party/               第三方源码（Windows 与 macOS 共用）
  rkdeveloptool/           修改版 rkdeveloptool；port/ 为本仓库补充的配置与头文件
  libusb/                  libusb 上游源码
```

## 依赖方向

```text
                         launcher
                 ┌──────────┴──────────┐
          platforms/linux       platforms/windows        平台差异（互不依赖）
          适配器·宿主  desktop.rs  适配器·宿主  desktop.rs
              │          │          │          │
              │          └────┬─────┘          │
              │           frontend ────────────┼──┐      界面
              └──────────┬─────────────────────┘  │
                      runtime                     │      通用基础设施
                         │                        │
                    application ──────────────────┤      应用（实现 api）
                         │                        │
                       core               api · config   领域 / 契约
```

- 后端：`platforms/*` → `runtime` → `application` → `core`，`application` 实现 `api`。
- 前端：`frontend` 只依赖 `api`，不认识任何后端实现。
- 平台包的后端部分（适配器、宿主）不依赖界面；只有 `desktop.rs` 依赖 `frontend`，用来提供界面配置。

## 前后端一一对应

api 的每个模块对应前端的一个功能区；同名文件贯穿三层：

| api 模块 | 接口 | 前端动作层 | 前端视图 | 后端实现 |
|---|---|---|---|---|
| `device` | `DeviceApi` | `actions/device.rs` | 顶栏设备状态（`chrome.rs`） | `service/device.rs` |
| `task` | `TaskApi` | `actions/task.rs` | 状态栏进度、停止任务（`chrome.rs`） | `service/task.rs` |
| `download` | `DownloadApi` | `actions/download.rs` | `pages/download.rs` | `service/download.rs` |
| `upgrade` | `UpgradeApi` | `actions/upgrade.rs` | `pages/upgrade.rs` | `service/upgrade.rs` |
| `advanced` | `AdvancedApi` | `actions/advanced.rs` | `pages/advanced.rs` | `service/advanced.rs` |
| `settings` | `SettingsApi` | `actions/settings.rs` | 顶栏工具按钮、日志目录 | `service/settings.rs` |
| `log` | `LogApi` | `actions/log.rs` | 运行终端 | `service/log.rs` |
| `workspace` | `WorkspaceApi` | `actions/workspace.rs` | 配置导入导出 | `service/workspace.rs` |

前端（`crates/frontend/src/desktop/`）内部再分两层：

- **视图**：`pages/`、`chrome.rs`、`overlays.rs` 只负责绘制和收集输入，调用动作层方法。
- **动作层**：`actions/<模块>.rs` 是前端唯一调用后端的地方，每个文件只调用同名 api 模块的接口。

会改变设备的操作都成对提供 `check_*` 与执行函数。动作层的 `request_*` 先调用 `check_*`，
校验通过才弹出确认框，用户确认后才执行。以下载镜像为例：

```text
pages/download.rs “开始下载”
  → actions/download.rs request_download()  → DownloadApi::check_download()     校验
  → 确认框 → actions/download.rs download_images() → DownloadApi::download_images() 执行
  → service/download.rs → FlashPlanner（平台适配器）规划命令 → runtime 执行
```

## 各层职责

| 层 | 位置 | 负责 | 不允许 |
|---|---|---|---|
| 领域 | `crates/core` | RKFW/RKAF 固件解析与 MD5、GPT/parameter 识别、标准分区表、芯片识别、工具输出识别、rkdeveloptool 协议、烧录工作流 | 依赖任何其他 crate、界面、进程管理 |
| 契约 | `crates/api`、`crates/config` | 各功能区的接口与请求类型、设备状态、执行事件、工具能力 `ToolInfo`；工作区配置模型 | 依赖实现、界面或系统能力 |
| 应用 | `crates/application` | `service/` 实现各 api 接口；统一的执行前校验；内部命令 `FlashOperation`；端口定义 | 访问文件系统或进程，依赖运行时、平台或界面 |
| 通用基础设施 | `crates/runtime` | 外部工具串行执行与取消、工作流会话、设备轮询、操作日志、工作区持久化、工具发现、装配 | 平台条件编译与系统专有 API、烧录工具或厂商细节 |
| 界面 | `crates/frontend` | 视图、动作层、组件、主题、文件对话框；平台差异由 `DesktopProfile` 注入 | 依赖 api 以外的 crate、平台条件编译、按工具名分支、视图直接调用 api |
| 平台 | `platforms/linux` | upgrade_tool 适配器、Unix 宿主、Linux 字体与渲染器、.deb 打包 | 依赖 Windows 平台或 Win32 API |
| 平台 | `platforms/windows` | rkdeveloptool 适配器、Win32 宿主、Windows 字体与 wgpu 渲染器、安装程序与 WinUSB 驱动 | 依赖 Linux 平台或 Unix API |
| 平台 | `platforms/macos` | SwiftUI 原生应用、Xcode 工程、.dmg 打包 | — |
| 启动 | `crates/launcher` | 选择平台包，组装 `create_application()` 与 `desktop_profile()` 并启动界面 | 业务、设备或界面实现 |

## 三个扩展点

平台差异只通过三个接口进入通用代码。新增平台时只需新建 `platforms/<名称>`：

1. **烧录工具**：实现应用层的 `FlashPlanner` 与 `ToolProtocol`。`FlashPlanner` 把操作规划为命令或工作流，
   并用 `tool_info()` 声明支持哪些查询、控制和存储；`ToolProtocol` 负责解析设备列表、进度和失败。
2. **操作系统**：实现运行时的 `OsHost`（工具进程配置与终止、进程存活判断、本地时间、
   工具日志目录映射）。
3. **桌面界面**：提供 `frontend::desktop::DesktopProfile`（中文字体候选、渲染器顺序、启动失败提示）。

平台包用 `runtime::assemble_application(ToolBackend { .. }, host)` 装配后端，
再由 `launcher` 调用 `frontend::desktop::run(application, desktop_profile())`。

## 平台差异一览

| | Linux | Windows | macOS |
|---|---|---|---|
| 目录 | `platforms/linux` | `platforms/windows` | `platforms/macos` |
| 烧录工具 | upgrade_tool（闭源，构建时下载） | rkdeveloptool（`third_party/`） | rkdeveloptool（`third_party/`） |
| 整包升级 | 工具内置 `UF` | core 工作流 | Swift 实现 |
| 工具能力 | 全部查询与控制 | 部分查询；控制仅支持重启；无串口日志；无 SPI NAND | — |
| 进程与日志 | 进程组、HOME 下日志软链接 | 无窗口启动、日志目录环境变量 | — |
| 界面渲染 | OpenGL | wgpu（Direct3D），失败退回 OpenGL | SwiftUI |
| USB 权限 | udev 规则 | WinUSB（libwdi） | 无需驱动 |
| 打包 | `packaging/`（Docker → .deb） | `packaging/`（MinGW + NSIS） | `Makefile`（.dmg） |

## 自动校验

`platforms/linux/packaging/build.sh architecture`（CI 的 Linux 检查会执行）会逐条检查上表的“不允许”。
下面这些情况都会让构建失败：
- runtime 中出现 `cfg(windows)`；
- 前端视图绕过 `actions/` 直接调用 api；
- 前端按工具名分支；
- 平台适配器依赖界面；
- 两个平台包互相依赖。
