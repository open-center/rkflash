# 分层架构

RKFlash 有三个平台版本：Linux 与 Windows 共用一套 Rust 代码，macOS 是 SwiftUI 原生版。
Rust 代码按“通用分层 + 平台拆包”组织：通用部分逐层解耦，三个平台的差异各自放在独立的包里。

## 总览

```text
                         ┌──────────────┐
                         │   launcher   │  按目标平台选择一个平台包装配并启动
                         └──────┬───────┘
                ┌───────────────┴───────────────┐
        ┌───────▼────────┐              ┌───────▼────────┐        ┌──────────────┐
        │ platforms/linux│              │platforms/windows│        │   frontend   │  egui 界面
        │ upgrade_tool   │              │ rkdeveloptool   │        └──────┬───────┘
        │ Unix 宿主      │              │ Win32 宿主      │               │
        └───────┬────────┘              └───────┬────────┘               │
                └───────────────┬───────────────┘                        │
                        ┌───────▼───────┐                                │
                        │    runtime    │  进程执行、设备轮询、日志、持久化│
                        └───────┬───────┘                                │
                        ┌───────▼───────┐        ┌──────────────┐        │
                        │  application  │───────►│ api / config │◄───────┘
                        └───────┬───────┘        └──────────────┘
                        ┌───────▼───────┐
                        │     core      │  固件、分区、芯片、协议、烧录工作流
                        └───────────────┘

  macOS：macos/（SwiftUI）+ native/（rkdeveloptool + libusb，与 Windows 共用）
```

依赖只朝下：`launcher → platforms/* → runtime → application → core`，`frontend → api`。
`frontend` 与后端之间只通过 `api` 中的 `FlashService` 交互，两边可以独立替换。

## 各层职责

| 层 | crate | 负责 | 不允许 |
|---|---|---|---|
| 领域 | `core` | RKFW/RKAF 固件解析与 MD5、GPT/parameter 识别、标准分区表、芯片识别、工具输出识别、rkdeveloptool 协议、下载/整包升级/擦除工作流 | 依赖任何其他 crate、界面、进程管理 |
| 契约 | `api`、`config` | 前后端唯一接口（类型化操作、设备状态、执行事件、`FlashService`）；工作区配置模型与 JSON | 依赖实现、界面或系统能力 |
| 应用 | `application` | `FlashApplication` 用例门面、操作校验、镜像路径解析、执行计划、端口定义（trait）、通用下载列表规则 | 访问文件系统或进程，依赖运行时、平台或界面 |
| 通用基础设施 | `runtime` | 外部工具串行执行与取消、工作流会话、设备轮询、操作日志、工作区持久化、工具发现、应用装配 | 平台条件编译与系统专有 API、任何烧录工具或厂商细节 |
| 界面 | `frontend` | 页面、组件、主题、文件对话框；平台差异只在 `desktop/platform/` | 依赖 api 以外的 crate、启动进程 |
| 平台 | `platforms/linux` | upgrade_tool 适配器（命令规划、输出协议）、Unix 宿主（进程组、localtime_r、日志软链接） | 依赖 Windows 平台或 Win32 API |
| 平台 | `platforms/windows` | rkdeveloptool 适配器（映射到 core 工作流）、Win32 宿主（无窗口启动、进程查询、本地时间） | 依赖 Linux 平台或 Unix API |
| 装配 | `launcher` | 选择平台包，调用 `create_application()` 并启动界面 | 业务、设备或界面实现 |

## 两个扩展点

平台差异只通过两个接口进入通用代码，新增平台时只需新建一个 `platforms/<名称>` 包：

1. **烧录工具**：实现应用层的 `FlashPlanner`（把类型化操作规划为命令或工作流）与
   `ToolProtocol`（设备列表、进度、失败识别）。
2. **操作系统**：实现运行时的 `OsHost`（工具进程配置与终止、进程存活判断、本地时间、
   工具日志目录映射）。

平台包用 `runtime::assemble_application(ToolBackend { .. }, host)` 完成装配。

## 平台差异一览

| | Linux | Windows | macOS |
|---|---|---|---|
| 平台包 | `crates/platforms/linux` | `crates/platforms/windows` | `macos/`（Swift） |
| 烧录工具 | upgrade_tool（闭源） | rkdeveloptool（`native/`） | rkdeveloptool（`native/`） |
| 整包升级 | 工具内置 `UF` | core 工作流 | Swift 实现（计划改用 core） |
| 进程与日志 | 进程组、HOME 下日志软链接 | 无窗口启动、日志目录环境变量 | — |
| USB 权限 | udev 规则 | WinUSB（libwdi） | 无需驱动 |
| 打包 | `packaging/linux`（Docker → .deb） | `packaging/windows`（MinGW + NSIS） | `macos/Makefile`（.dmg） |

## 自动校验

`packaging/linux/build.sh architecture`（CI 的 Linux 检查会执行）逐层检查上表中的“不允许”，
例如 runtime 中出现 `cfg(windows)`、应用层访问文件系统、前端依赖实现 crate，都会让构建失败。
