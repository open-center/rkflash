# rkflash 分层架构

## 依赖方向

```text
rkflash-launcher ──> rkflash-frontend ──> rkflash-api ──> rkflash-config
        │                                      ▲
        └────────> rkflash-backend ────────────┘
                          └────────────────────────> rkflash-config
```

- `app/api`：前后端唯一共享契约，定义类型化操作、设备状态、执行事件、配置导出和
  `FlashService` 能力端口；不依赖 GUI、进程、文件系统或具体适配器。
- `app/config`：镜像项、工作区等可序列化配置模型与 JSON codec，不依赖设备、
  GUI、进程或文件系统。
- `app/backend/src/domain`：后端内部执行计划，不访问系统资源；跨边界类型统一来自 `api`。
- `app/backend/src/application`：`facade.rs` 提供唯一前后端门面，`ports/` 按执行、监控、
  工具定位、日志、规划、文件系统和工作区仓储拆分接口，`validation.rs` 和
  `image_resolution.rs` 保存与适配器无关的用例规则。
- `app/backend/src/infrastructure/process`：通用外部工具适配，按 `command`、`monitor`、
  `logging`、`terminal` 和 `runtime` 分离进程环境、只读轮询、日志、终端清洗与任务协调。
- `app/backend/src/infrastructure/persistence`：工作区仓储和本地文件系统是两个独立适配器。
- `app/backend/src/infrastructure/rockchip`：Rockchip 特殊实现，包括默认分区、分区参数、
  Loader 存储映射、`upgrade_tool` 命令码、输出解析和工具发现。
- `app/frontend`：egui 前端、页面、组件和视图状态，只依赖 `api` 并提交类型化操作，
  不依赖 `backend`、不构造命令行，也不启动进程。
- `app/launcher`：唯一二进制，只连接后端应用门面与桌面前端，不放业务或 UI 实现。

`rkflash-backend::create_application` 封装后端内部适配器装配，launcher 将其作为
`rkflash_api::FlashService` 交给 `rkflash_frontend::desktop::run`。前端不知道、也不能直接
依赖 `FlashApplication`、`ProcessRuntime` 或 `UpgradeToolAdapter`。

frontend crate 内继续按职责拆分：`pages/` 保存三类工作流页面，`actions.rs` 处理用户动作，
`layout.rs` 提供内容驱动的响应式布局策略，`chrome.rs` 负责窗口导航、状态与终端外壳，
`overlays.rs` 统一错误、设备状态提示和高风险确认浮层。页面不再复制这些全局布局与反馈逻辑。

## 通用逻辑与特殊配置

通用逻辑通过细粒度应用端口表达：

- `OperationExecutor`：运行、取消和收集任务事件。
- `DeviceMonitor`：只读发布设备快照。
- `ToolLocator`：读取和切换外部工具路径。
- `OperationLog`：管理工具日志目录和单次操作日志。
- `FlashPlanner`：把类型化操作规划为执行步骤。
- `FlashProfile`：提供默认镜像项和 parameter 解析能力。
- `ToolProtocol`：提供设备扫描和输出解析协议。
- `WorkspaceRepository`：只负责工作区配置持久化。
- `FileSystem`：只提供用例所需的最小文件查询能力。

`FlashApplication` 只协调这些端口，不调用 `std::fs`、`std::process` 或 Rockchip 模块。
`ProcessRuntime` 可以同时实现多个细粒度端口以共享串行锁和任务状态，但应用层只看到各自接口。
固定的 `upgrade_tool/log` 相对路径由 Rockchip 适配器注入，通用进程层不感知厂商名称。

Rockchip 细节只在 `app/backend/src/infrastructure/rockchip` 实现。新增其他工具或芯片平台时，
应增加新的适配器并在组合根切换注入，不能在 GUI 中增加工具名判断或命令码分支。

## 强制边界

构建 Debian 安装包时会自动检查依赖方向和特殊命令泄漏：

```bash
./build.sh architecture
```

Debian 构建脚本也会先执行该检查。新增功能应继续满足：

1. `api` 和 `config` 不依赖 backend、frontend、文件系统、进程或 GUI。
2. `backend` 实现 `api` 端口但不依赖 frontend，应用和领域模块不依赖具体 Rockchip 实现。
3. `frontend` 只依赖 `api`，不依赖 backend，不直接读取固件、工作区或设备文件，
   不使用 `std::process`，不出现
   `upgrade_tool` 命令码；界面专用系统字体读取隔离在 `desktop/platform`。
4. `launcher` 只装配 backend 与 frontend，不包含业务、设备或 UI 实现。
5. 外部进程只允许由 `app/backend/src/infrastructure/process` 创建。
6. 平台特例以配置、枚举映射或适配器实现下沉，不以 UI 条件分支扩散。
7. 通用进程层不出现 Rockchip、`upgrade_tool` 或厂商命令码；厂商运行时约束通过组合根注入。

## 出包脚本分层

仓库只提供一个根目录可执行入口，内部模块不作为用户命令直接运行：

```text
build.sh                        # 唯一用户入口；宿主转入容器，容器内负责参数分发
Dockerfile                      # 固定 Ubuntu、Rust、系统库与打包工具
scripts/docker.bash             # 宿主组合根；只装配项目配置、基础设施和交付工作流
scripts/docker-entrypoint.sh    # 初始化容器内可写缓存并回到 build.sh
scripts/lib/common.bash         # 命令、环境、Rust 和 ELF/ABI 通用能力
scripts/lib/rust.bash           # Rust 构建、运行、测试、检查和清理流程
scripts/lib/debian.bash         # Debian 与离线依赖通用出包流程
scripts/lib/container.bash      # 通用 Docker 镜像、容器运行和断网安装验证
scripts/lib/delivery.bash       # 通用 package/offline/offline-all 生命周期编排
scripts/config/rkflash.bash     # rkflash/Rockchip 配置、文件布局和项目钩子
scripts/config/rkflash-delivery.bash # Ubuntu 矩阵、镜像覆盖规则和交付验收清单
```

脚本依赖方向固定为：

```text
build.sh(host)
  -> scripts/docker.bash (组合根)
    -> config/rkflash*.bash (项目与平台策略)
    -> lib/delivery.bash (交付用例编排)
      -> lib/container.bash (Docker 基础设施)
        -> build.sh(container)
          -> lib/rust.bash | lib/debian.bash
```

`lib` 只调用稳定的 `project_*` 钩子，不包含 rkflash、Rockchip、`upgrade_tool`、固定 Ubuntu
版本、图标、udev 规则或包兼容名称。项目文件布局、厂商二进制、Ubuntu 版本矩阵、镜像环境
变量和安装验收路径全部下沉到 `config/`。`project_validate_sources` 会持续检查这条边界，避免
后续修改重新把特殊逻辑写回通用层。

`setup`、`toolchain`、`release`、`run`、`fmt`、`test`、`lint`、`architecture`、`check` 和
`clean` 属于开发生命周期；`build`、`package`、`install`、`offline` 与 `offline-all` 属于交付生命周期。
`build` 是默认出包命令，`package` 是其别名；两者固定在 Ubuntu 22.04 编译唯一跨版本
`.deb`，并在交付目录生成复用同一实现的 `install.sh`。`install` 是唯一允许调用宿主 `sudo`/APT 的显式安装动作，
它和交付安装器都会先把包复制到 `_apt` 可访问的 `/var/tmp` 暂存目录；构建流程本身仍不修改宿主软件。离线流程再进入 22.04/24.04/26.04
目标容器解析各自依赖，并在禁网的干净基础容器中实装验证。系统包和
stable Rust 由 Dockerfile 一次性装入镜像，运行构建命令时不修改宿主机。`clean` 只删除 Cargo 的
项目内统一的 `output/`，不会清理项目外路径，也不依赖 Cargo。Cargo 编译内容位于
`output/target/`，安装包和离线交付物位于 `output/dist/`。
