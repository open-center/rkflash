# 构建脚本体系详解

整套构建体系的核心设计：**宿主只装 Docker，一切构建发生在版本固定的容器内**；并通过
"通用流程层（`scripts/lib`）+ 项目配置钩子层（`scripts/config`）"分离实现复用。

```text
宿主机                                    Docker 容器（版本固定的 Ubuntu 镜像）
──────                                    ─────────────────────────────────
./build.sh <cmd>                          /workspace/build.sh <cmd>（同一脚本！）
   │                                          │
   │ CONTAINERIZED_BUILD != 1 或无 /.dockerenv│ 容器内：CONTAINERIZED_BUILD=1 且存在 /.dockerenv
   ▼                                          ▼
scripts/docker.bash（宿主组合根）            source lib/common + rust + debian
   │                                          + config/rktools*.bash
   ▼                                          ▼
lib/delivery.bash（生命周期编排）             命令 case 分发 → rust_* / debian_*
   │
   ▼
lib/container.bash（镜像/容器/断网验证）
   │
   ▼
docker run → 容器内 build.sh → 编译 / 打包 / 离线闭包求解
```

分层职责边界（由 `project_validate_sources` 用 ripgrep 强制检查）：

| 层 | 职责 | 禁止内容 |
|---|---|---|
| [build.sh](../build.sh) | 只做装配和参数分发 | `apt-get`、`dpkg-deb`、`cargo build`、`upgrade_tool` 等业务实现 |
| [scripts/lib/](../scripts/lib) | 通用流程 | `rktools`、`rockchip`、`upgrade_tool`、`71-rktools`、`RKTOOLS_`、固定发行版版本字样 |
| [scripts/config/](../scripts/config) | 项目差异唯一注入点 | ——（包名、依赖组、文件布局、交付矩阵、镜像策略全在这） |

脚本调用关系：

```text
build.sh(host)
  -> scripts/docker.bash (组合根)
    -> config/rktools*.bash (项目与平台策略)
    -> lib/delivery.bash (交付用例编排)
      -> lib/container.bash (Docker 基础设施)
        -> build.sh(container)
          -> lib/rust.bash | lib/debian.bash
```

## 1. build.sh —— 唯一用户入口

既是宿主入口（转发给 docker.bash），也是容器内入口（命令分发）。通过
`CONTAINERIZED_BUILD` 环境变量与 `/.dockerenv` 文件**双重判定**当前环境：

```bash
if [[ "${CONTAINERIZED_BUILD:-0}" != 1 || ! -f /.dockerenv ]]; then
    exec "$SCRIPTS_DIR/docker.bash" "$@"     # 宿主路径
fi
# 容器内：装配后进入命令分发
```

容器内装配顺序：`lib/common.bash` → `config/rktools.bash` → `config/rktools-delivery.bash`
→ `lib/rust.bash` → `lib/debian.bash` → 校验 `Cargo.toml` 存在 → `project_configure` +
`project_delivery_configure` 注入项目配置。

### 命令分发表

无参数默认 `build`。两个生命周期：

**开发生命周期**：

| 子命令 | 容器内实现 | 说明 |
|---|---|---|
| `release` | `rust_build_release` | 只构建 Rust release 二进制 |
| `setup` | 依赖准备 + `rust_update_toolchain` | 拉取最新基础镜像重建并准备环境 |
| `toolchain` | `rust_update_toolchain` | 不用缓存完整重建镜像 |
| `run [参数...]` | `rust_run "$@"` | 运行桌面程序，参数透传（含 GUI/USB 透传） |
| `fmt` / `test` / `lint` | `rust_format` / `rust_test` / `rust_lint` | 格式检查 / 全部测试 / Clippy（警告即错误） |
| `architecture` | `rust_check_architecture` | 分层边界检查 |
| `check` | `rust_check` | 依次 fmt → architecture → test → lint |
| `clean` | `rust_clean` | 清理整个 `output/` |

**交付生命周期**：

| 子命令 | 说明 |
|---|---|
| `build` / `package` | 等价别名：release 编译 + 生成 `.deb`，**固定 Ubuntu 22.04 基线** |
| `install` | 宿主处理：安全暂存并安装已生成的 `.deb`，不重新构建 |
| `offline` / `offline-all` | **容器内直接报错**（宿主专用，需跨版本容器编排） |
| `offline-bundle` | 容器内专用：复用基线 `.deb` 为当前镜像版本生成离线包 |

## 2. Dockerfile —— 构建器镜像

单阶段构建（镜像同时承担"构建环境"与"离线依赖解析环境"）。关键构建参数：
`UBUNTU_VERSION`（默认 22.04）、`UBUNTU_IMAGE`（基础镜像整体覆盖）、
`UBUNTU_APT_MIRROR`（APT 换源）、`CUSTOM_CA_CERT_B64` / `EXTRA_CA_CERT_B64`
（base64 编码 PEM 证书注入信任链）、代理变量（显式声明以兼容传统构建器）。

系统层 RUN 块的关键顺序设计：

1. **先快照干净 dpkg 状态**到 `/var/lib/dpkg/status.clean-base`
   ——供 offline-bundle 求解"干净基线系统的依赖闭包"；
2. `apt-get update` → **先装 `ca-certificates`**（部分镜像变体无 CA bundle，
   不先引导会导致后续 https 下载全挂）→ 注入自定义 CA；
3. APT 镜像替换（对 sources.list 与 .sources 做 sed）；
4. 安装构建+打包合一的系统包（`--no-install-recommends`）：编译工具链、
   GUI 开发库（mesa/wayland/x11/xi/xkbcommon）、`libusb-1.0-0-dev`/`libudev-dev`、
   `dpkg-dev`、`desktop-file-utils`、`binutils`、`ripgrep`（架构检查用）；
5. 清缓存但**故意保留 APT 索引**（离线闭包求解需要）。

Rust 工具链：从 `rust-toolchain.toml` 解析 channel（当前 **1.98.1**）后 rustup 安装
minimal + clippy + rustfmt。**固定具体版本，不跟随 stable 漂移**——任何时间重建镜像
都得到同一套编译器；升级时显式修改该文件。

镜像固化环境变量：`CONTAINERIZED_BUILD=1`（双路径判定）、`RUST_BOOTSTRAP_DISABLED=1`
与 `SYSTEM_BOOTSTRAP_DISABLED=1`（禁止容器内脚本自动装 Rust/系统包）、
`BASELINE_DPKG_STATUS`（干净 dpkg 快照路径）。

入口：`WORKDIR /workspace`（宿主 bind mount 项目根）+
ENTRYPOINT 指向 [scripts/docker-entrypoint.sh](../scripts/docker-entrypoint.sh)。

### docker-entrypoint.sh —— 容器内初始化

1. 校验 `/workspace` 挂载存在（防误用镜像）；
2. 创建可写目录：`$HOME`（= /tmp/delivery-home）、`$CARGO_HOME`
   （= /workspace/output/docker/cargo-home）、target 目录——**可写缓存必须放在
   bind mount 内而不是容器层**；容器以宿主用户 uid/gid 运行，产物宿主可编辑；
3. `exec /workspace/build.sh "$@"` 把命令原样交回项目入口脚本。

## 3. lib/ —— 通用流程层

### 3.1 [common.bash](../scripts/lib/common.bash) —— 通用能力

| 函数 | 用途 |
|---|---|
| `packaging_die` / `packaging_require_command` | 统一错误与命令存在性检查 |
| `packaging_remove_output_dir` | **安全删除**：规范化路径后要求产出目录必须位于项目根之下，否则拒绝清理项目外目录 |
| `packaging_recreate_output_dir` | 出包前安全清空 `output/dist/` |
| `packaging_check_debian_dependencies` | dpkg-query 逐包确认；容器内缺依赖提示"请更新 Dockerfile 重建镜像" |
| `packaging_prepare_rust_toolchain` | 探测（选最新候选）→ 版本门槛（≥ `RUST_MINIMUM_VERSION`，本项目 1.88）→ 不满足则 bootstrap |
| `packaging_rust_can_compile` | 编译探针：`fn main(){}` 真实验证工具链能编译宿主目标 |
| `packaging_assert_no_matches` | 架构检查原语：ripgrep 命中即 die |
| `packaging_check_elf_glibc` | **ELF/ABI 检查**：`file` 确认 x86-64、`readelf --version-info` 取最高 `GLIBC_x.y` 与基线比较；静态链接直接放行 |

日志前缀约定：`[环境] [产出] [Docker] [交付] [验证] [安装]` 与 `[1/4]…[4/4]` 步骤序号。

### 3.2 [rust.bash](../scripts/lib/rust.bash) —— Rust 工作区流程

所有 cargo 命令带 `--locked`（锁定依赖，可复现构建）：
`rust_build_release` / `rust_run` / `rust_format`（只检查不修改）/ `rust_test` /
`rust_lint`（`-D warnings`）/ `rust_check_architecture`（装配 ripgrep 后调
`project_validate_sources`）/ `rust_check`（四步顺序，任一失败即中止）/ `rust_clean`。
`rust_update_toolchain` 容器内只做检查并提示"工具链已固化在镜像中"。

### 3.3 [debian.bash](../scripts/lib/debian.bash) —— 出包流程

**`debian_build_package`（`[1/4]`–`[4/4]`）**：

1. **基线校验**：容器内读 `/etc/os-release`，发行版/版本必须等于注入的
   `DELIVERY_BASELINE_*`（ubuntu 22.04），否则拒绝出包；
2. **环境校验**：strict 依赖检查、架构必须 amd64、Rust 工具链可用；
   `project_validate_sources`（架构边界）+ `project_validate_package_inputs`
   （物料校验，含 upgrade_tool 的 sha256 核对）；
3. `[1/4]` `cargo build --release --locked` → `project_validate_binary`
   （主程序与 upgrade_tool 均做 ELF/glibc 检查，基线 2.35）；
4. `[2/4]` 生成 Debian 文件树（stage 目录 chmod 0755——mktemp 默认 0700 会被
   dpkg-deb 写进包根权限）、`project_stage_payload` 安装文件、计算
   `Installed-Size` 与 `Depends`（来自 [runtime-dependencies.txt](../packaging/runtime-dependencies.txt)）、
   写 control 与维护脚本；
5. `[3/4]` 校验元数据，确定产物路径；
6. `[4/4]` `dpkg-deb --root-owner-group --build` 生成 `.deb`；把
   [scripts/install-deb.bash](../scripts/install-deb.bash) 以 0755 复制为
   `output/dist/install.sh`。

**`debian_build_offline_bundle_from_package`（离线包）**：

- **复用基线 `.deb`**：核对 Package/Version/Architecture 三个字段；
- **依赖闭包求解**：以 `BASELINE_DPKG_STATUS`（镜像内干净快照）为 dpkg 状态基线，
  `apt-get --simulate install <运行时包>` 求出基线系统缺少的包闭包
  （解析 `Inst` 行时需处理"新装"与"升级"两种形态）；
- **下载与校验**：`apt-get --print-uris` 得到 URL/大小/SHA-512 计划，
  按大小 + SHA-512 双重校验后原子落盘；
- 写 `README.txt`、`BUILD-INFO`，生成 `install.sh`、`SHA256SUMS`，tar.gz
  （先写临时文件再 `mv` 原子入 dist），同时产出 `.sha256`。

**离线安装器 `install.sh` 的设计**（源码注释明确动机）：

- **本地 `file:` 仓库而非命令行直传 `.deb`**——直传在升级已装包时触发 apt 的
  "Pathname to install is not absolute" 内部错误，且无法表达"保留目标机上比包内
  更新的版本"；仓库方式两者都正确；
- 暂存到 `/var/tmp`（`_apt` 沙箱可读），Packages 索引用 `dpkg-deb -f` 生成完整
  control 字段（缺了依赖信息 apt 会把所有包当零依赖），显式 chmod 0644；
- **源隔离**：独立 sources.list + `Dir::Etc::sourceparts=/dev/null`（除本地仓库外
  无任何软件源，**天然禁止联网**）+ 独立索引目录，不触碰目标机 APT 状态。

### 3.4 [container.bash](../scripts/lib/container.bash) —— Docker 基础设施

- `container_require_engine`：docker 存在且 daemon 可达；
- `container_ensure_builder_image`：三种重建策略（`normal` 仅本地无 tag 时构建 /
  `pull` 强制拉最新基础镜像 / `no-cache` 完全重建）；代理变量自动透传为
  `--build-arg`；镜像名、基础镜像、APT 镜像全部来自配置钩子；
- `container_run_builder`：`--user $(id -u):$(id -g)`（以宿主用户身份运行）、
  bind mount 项目根、注入 `HOME`/`CARGO_HOME`/`CARGO_TARGET_DIR`（package 命令
  使用独立的 `delivery-ubuntu-22.04` target 目录，不复用其他版本容器的链接产物）、
  **白名单转发**环境变量（见 §6）、`run` 命令的桌面/设备透传：
  - X11：挂载 `/tmp/.X11-unix` + Xauthority；
  - Wayland/DBus：**只挂载确需的单个 socket 文件而不是整个 XDG_RUNTIME_DIR**
    （避免把 SSH agent、PulseAudio 等一并暴露给容器）；
  - USB：挂载 `/dev/bus/usb` + `--device-cgroup-rule "c 189:* rmw"`
    （189 为 USB 主设备号，Rockchip 设备烧写需要）；
- `container_verify_offline_bundle`：**断网安装验证**——在干净的基础镜像（非构建器
  镜像）中以 `--network none` 运行：两层 sha256 校验 → 真实执行 `install.sh` →
  dpkg 包状态 → 逐个 `test -x`/`test -f` 校验主程序、厂商工具、udev 规则和桌面入口。

### 3.5 [delivery.bash](../scripts/lib/delivery.bash) —— 宿主生命周期编排

`delivery_dispatch` 分发：

| 命令 | 编排 |
|---|---|
| `clean` / `install` | **本地直接处理，不经过 Docker** |
| `build` / `package` | `delivery_build_package primary`（.deb 永远在 22.04 基线容器构建） |
| `offline` | 校验目标版本 → 基线 `.deb` → 目标版本镜像内求解闭包 → 断网验证 |
| `offline-all` | 一次基线 `.deb` → 遍历 22.04/24.04/26.04 逐一离线包+验证 |
| `setup` | `pull` 策略重建镜像后进容器准备环境 |
| `toolchain` | `no-cache` 完全重建 |
| 其他（release/run/fmt/…） | ensure 镜像 → 原样转发进容器 |

**role 语义**：`primary`=开发主镜像（`RKTOOLS_UBUNTU_VERSION` 指定）、
`baseline`=基线出包镜像（固定 22.04）、`target`=offline-all 的目标版本镜像。
role 决定选用哪一组镜像覆盖环境变量。

## 4. config/ —— 项目配置钩子层

### 4.1 [rktools.bash](../scripts/config/rktools.bash) —— 项目与打包配置

`project_configure` 设置：包名 `rktools`、版本（从 `Cargo.toml` 的
`[workspace.package]` 段解析）、架构 amd64、包元数据（Conflicts/Replaces/Provides
`rk-flash-studio (= 版本)`——带版本才能满足版本约束）、`GLIBC_BASELINE=2.35`、
目录布局（`OUTPUT_ROOT`/`DIST_DIR`/`RELEASE_BINARY`/`UPGRADE_TOOL`）等。

四个依赖组：`bootstrap`（rustup 下载）、`development`（编译/测试）、
`architecture`（ripgrep）、`packaging`（出包全量，**strict**——必须 dpkg 包级安装，
命令存在不算数）。

`project_validate_sources` —— **架构边界检查规则全集**（构建安装包时自动执行），
要点：通用脚本层禁项目字样、契约/配置/后端 crate 禁 GUI 框架、进程执行只能留在
infrastructure/process、应用/领域层禁依赖基础设施、通用进程层禁 Rockchip 命令码
（LD/DI/WL/UF/EF/RL/EL 等全表）、前端禁命令码与后端实现、launcher 禁业务实现。

`project_stage_payload` —— `.deb` 文件布局：

```text
usr/bin/rktools                                   0755（release 二进制，随后 strip）
usr/lib/rktools/upgrade_tool                      0755
usr/lib/udev/rules.d/71-rktools.rules            0644
usr/share/applications/rktools.desktop            0644（desktop-file-validate 校验）
usr/share/icons/hicolor/scalable/apps/rktools.svg   + 256x256 PNG
usr/share/doc/rktools/{README.md,THIRD_PARTY.md,copyright}
```

维护脚本：`postinst` 重载 udev 规则并触发 Rockchip VID 2207 设备、刷新桌面数据库；
`postrm` 在 remove/purge 时做同样刷新。

### 4.2 [rktools-delivery.bash](../scripts/config/rktools-delivery.bash) —— 交付矩阵

关键配置：基线 `22.04`、目标矩阵 `(22.04 24.04 26.04)`、容器路径常量
（`/workspace`、`/tmp/delivery-home`、cargo 缓存与独立出包 target 目录）、
验证清单（主程序/厂商工具 `test -x`，udev/desktop `test -f`）、环境变量透传白名单。

**镜像覆盖三级优先级**（`project_delivery_*` 钩子）：

1. 按版本覆盖：`RKTOOLS_UBUNTU_IMAGE_22_04`（版本点号转下划线）——优先级最高；
2. 按角色：`RKTOOLS_BASELINE_UBUNTU_IMAGE`（baseline）/ `RKTOOLS_UBUNTU_IMAGE`（primary）；
3. 默认：`ubuntu:<版本>`、构建器镜像 `rktools-builder:ubuntu-<版本>`。

## 5. 目录布局与产物命名

```text
output/                                  # clean 命令整体删除，不碰项目外路径
├── target/                              # 开发编译目录（.cargo/config.toml 固定）
│   └── delivery-ubuntu-22.04/           # 正式出包专用独立 target
├── docker/cargo-home/                   # 容器内 CARGO_HOME（bind mount 内可写缓存）
└── dist/                                # 交付物（build/offline 前先安全清空）
    ├── rktools_<版本>_amd64.deb
    ├── install.sh
    └── rktools_<版本>_ubuntu-<22.04|24.04|26.04>_amd64_offline.tar.gz (+ .sha256)
```

离线包内部：`packages/*.deb`（应用包 + 依赖闭包）、`install.sh`、`README.txt`、
`BUILD-INFO`、`SHA256SUMS`。

## 6. 环境变量总表

**用户可配置（RKTOOLS_\* 系列）**：

| 变量 | 默认 | 作用 |
|---|---|---|
| `RKTOOLS_UBUNTU_VERSION` | 22.04 | 开发容器 / `offline` 目标版本 |
| `RKTOOLS_DOCKER_PLATFORM` | linux/amd64 | docker build/run 平台 |
| `RKTOOLS_DOCKER_REBUILD` | 0 | =1 强制重建镜像 |
| `RKTOOLS_DOCKER_CA_CERT` / `_EXTRA_CA_CERT` | 空 | 自定义 CA 证书（单张 PEM，≤32 KiB） |
| `RKTOOLS_UBUNTU_IMAGE` / `RKTOOLS_BASELINE_UBUNTU_IMAGE` | ubuntu:\<ver\> | 基础镜像覆盖 |
| `RKTOOLS_UBUNTU_APT_MIRROR` / `_BASELINE_` | 空 | APT 源镜像 |
| `RKTOOLS_DOCKER_IMAGE` / `_BASELINE_` | rktools-builder:ubuntu-\<ver\> | 构建器镜像名 |
| `RKTOOLS_<SETTING>_<VERSION>`（如 `_22_04`） | — | 按版本覆盖，优先级最高 |

**白名单透传进容器**：代理变量 ×6、`CARGO_NET_OFFLINE` / `CARGO_NET_GIT_FETCH_WITH_CLI`、
`RUST_BACKTRACE`、`RKTOOLS_LOG_DIR` / `RK_UPGRADE_TOOL`（应用运行时）、`SOURCE_DATE_EPOCH`。

**容器内注入**：`HOME`、`CARGO_HOME`、`CARGO_TARGET_DIR`、package 时的
`DELIVERY_BASELINE_*`、offline-bundle 时的 `OFFLINE_TARGET_*` 与 `OFFLINE_APT_MIRROR`、
run 时的桌面/DBus 变量。

## 7. 关键调用链速查

- **`./build.sh build`**：build.sh（宿主判定）→ docker.bash → delivery_dispatch →
  prepare_host → ensure 22.04 镜像 → run_builder（注入独立 target 目录与基线变量）→
  容器内 build.sh package → 四步出包（含架构检查、物料校验、ELF/glibc 检查）→
  dist 产出 `.deb` + `install.sh`。
- **`offline`（24.04 为例）**：校验目标 → 22.04 容器出基线 `.deb` → 24.04 容器
  offline-bundle（干净 dpkg 快照求闭包、下载双校验、组包）→ 回宿主用干净
  ubuntu:24.04 镜像 `--network none` 断网实装验证。
- **`run`**：ensure 镜像 → 容器（X11/Wayland/DBus socket 精准挂载 + USB 透传）→ cargo run。
- **`clean` / `install`**：宿主本地处理，**完全不经过 Docker**。
